# 2. 基本的な Slurm コマンドの確認

[Tutorial](README.md) | 前: [1. GMO クラウドへのログイン](01_login.md) | 次: [3. 開発コードのクローン](03_clone.md)

前章ではログインノードへの接続まで完了した。
この章では、計算ノードを使うための Slurm のコマンドをいくつか紹介する。

| command | 用途 |
| --- | --- |
| `snodes` | ノードとパーティションの状態を見る |
| `squeue -u $USER` | 自分のジョブの一覧と状態(`PD` は待ち、`R` は実行中)を見る |
| `srun ... --pty bash` | 計算ノードに対話的に入る |
| `sbatch job.sh` | ジョブスクリプトを投入する。ジョブ ID が表示される |
| `scancel <jobid>` | ジョブを止める |
| `sacct -j <jobid> --format=JobID,State,Elapsed,ExitCode` | 終わったジョブの結果を見る |

1. `snodes`コマンドを用いると使用可能なパーティション名を確認できる。今後はこのパーティション名を使っていく。

   ```bash
   snodes
   ```

2. 計算ノードに対話的に入り、`hostname` がログインノードのもの([1 章](01_login.md)で確かめた物)から変わった
   ことを確かめる。終わったら `exit` で抜ける(抜けるまで計算ノードを確保し続けるため注意)。

   ```bash
   srun --partition=<パーティション> --pty bash
   hostname
   exit
   ```

   GPU や CPU、時間を指定する時は `srun` にオプションを足す。GPU は `--gres=gpu:1`、
   CPU は `--cpus-per-task=16`、時間の上限は `--time=01:00:00` のように書く。
   その他のオプションについては適宜マニュアルを参照されたい。

3. 次に、実験として計算ノードのホスト名を書き出すだけのジョブを流す。
   チームの共用ストレージに自分用のディレクトリを作り、ログもそこに書く(以降の章もこのディレクトリで作業する)。

   ```bash
   mkdir -p <共用ストレージ>/<ユーザー名>/logs
   cd <共用ストレージ>/<ユーザー名>
   cat > hello.sh <<'EOF'
   #!/usr/bin/env bash
   #SBATCH --job-name=hello
   #SBATCH --partition=<パーティション>
   #SBATCH --output=<共用ストレージ>/<ユーザー名>/logs/%x-%j.out
   set -euo pipefail
   hostname
   date
   EOF
   sbatch hello.sh
   squeue -u $USER
   ```

   終わったら `logs/hello-<jobid>.out` に計算ノードのホスト名と実行された時刻が書き出される。
   `srun` と同じく、オプションを `#SBATCH --gres=gpu:1` のように書くと、GPU を確保できる。

## 共用ノードを使用する上での注意点

ログインノードも計算ノードも、1 台を複数のチームが共有している。自分のサーバーやデータを他のチームに公開しない
ために以下のような対策をする。なお、チュートリアルのコードはこの方式を使うように修正済みのため最新版を使うことを推奨する。

### サーバーを立てる時

`127.0.0.1`(localhost)は、サーバーを立てたノード自身を指すアドレスである。`127.0.0.1` で待ち受けるサーバーには、
同じノードにいる他のユーザーも接続できる。`127.0.0.1` に限るだけでは、自分やチームだけが使えるサーバーにはならない。
Jupyter や vLLM などのサーバーを自分で立てる時は、次のどちらかを行う。

1. サーバーの認証(トークンやパスワード)を使う。
2. 認証が使えない時は、TCP のポートの代わりに Unix domain socket(ソケットファイル)で待ち受け、ソケットを置く
   ディレクトリの権限で、接続できる人を限る。

- チームで使う時は、ディレクトリをチームのグループ領域に置いて `770` に、ソケットを `660` にする。どちらも所有
  グループがチームのグループであることを `ls -l` で確かめる。vLLM が作るソケットは、デフォルトではグループに書き込みの
  権限が無く、同じチームの人も接続できないので、起動した後に `chmod 660 <ソケット>` を実行する。
- ソケットで待ち受けさせるオプションの名前は、サーバーのソフトウェアごとに異なるため要確認(vLLM と uvicorn は `--uds <ソケット>`、
  Jupyter は `--sock <ソケット>`)。
- vLLM は `--uds` で立てても、エンジンのプロセスが内部の通信のために TCP のポートをいくつか開ける。推論の API は
  そこには無く、ソケットだけにあるため利用される可能性は低いが妨害を受ける可能性はある。このポートにも接続させないためには、
  ネットワークを切り離した名前空間の中で起動する(`unshare -r -n sh -c 'ip link set lo up; exec vllm serve ...'`)。
  名前空間の中からはダウンロードできないので、モデルはローカルの snapshot を指定する([setup.md](../setup.md) の Unix sockets)。

### データの置き場所と権限

- 認証情報(API キー、HuggingFace のトークン、SSH の鍵など)は、自分のホーム領域の、権限 `700` のディレクトリに置く。
  チームのグループ領域には置かない。
- その他の、他のチームに見せられないデータは、ホーム領域か、チームのグループ領域(`<共用ストレージ>`)に置く。
  チームで共有するディレクトリは `770` にする。
- `chmod 777` のように、他のユーザーにも広くアクセスを許す権限を付けない。

### 他のチームのサーバーやデータ

- 接続できる状態になっていても、他のチームのサーバーに意図して接続しない。競技のルールの違反になる。
- 他のチームの情報が見えるなど、意図せずアクセスできることに気付いた時は、それ以上見たり操作したりせず、運営に
  報告する。
